# Cost guardrails

The cost-side counterpart to the GuardDuty alerting path in this repository. That path
answers *is something attacking this account*. This one answers *is something costing
money that should not be* — the same question asked of the bill instead of the threat
feed, over the same SNS delivery.

One script, three controls, no console clicking:

```bash
pip install -r requirements.txt

python finops_alerts.py plan   --email you@example.com --monthly-limit 20   # changes nothing
python finops_alerts.py deploy --email you@example.com --monthly-limit 20
python finops_alerts.py status
python finops_alerts.py teardown --yes
```

`plan` needs no credentials and sends no mutating request. It prints every API call it
would make, generated by the same code that performs them — so the plan cannot drift
from the deploy the way a hand-written description would.

`deploy` is idempotent. Run it twice and the second run reports `exists` rather than
failing or creating duplicates.

---

## The three controls, and why one is not enough

| Control | What it is | What it catches that the others miss |
|---|---|---|
| **AWS Budgets** | A ceiling you set in advance, at 50%, 80% and 100% of actual spend plus 100% of forecast | The slow leak you forgot about. It is the only one of the three that fires on a **forecast** — before the money is gone rather than after |
| **Cost Anomaly Detection** | A model AWS trains on your own spend history, alerting immediately when today does not match your normal | The thing you never thought to set a ceiling on. That is Budgets' blind spot by design: a budget only watches what you told it to watch |
| **Cost allocation tags** | Not an alarm. Activating a tag key is what lets the other two say *which* project or environment the money went to | Nothing on its own — but without it an anomaly tells you the bill moved and nothing about where, which is most of the work |

## Architecture

```
  AWS Budgets ───────────────┐
  (threshold + forecast)     │
                             ├──▶  SNS topic  ──▶  email
  Cost Anomaly Detection ────┘      aws-cost-alerts
  (immediate, >= $5 impact)
```

**Note what is not in that diagram: EventBridge.** Budgets and Cost Anomaly Detection
each publish to SNS directly. The GuardDuty path in this repository *does* use
EventBridge, because GuardDuty emits findings onto the event bus and the rule is what
filters them by severity — cost alerts have no equivalent bus event, so there is nothing
for a rule to match on. The practical consequence is in the topic policy: it has to name
`budgets.amazonaws.com` and `costalerts.amazonaws.com` as publishers, not
`events.amazonaws.com`. Assuming the security wiring transfers is the mistake this note
exists to prevent, and a test asserts it does not regress.

## Decisions worth defending

Each of these is a choice with a cheaper alternative that is worse.

**The topic policy is scoped with `aws:SourceAccount`.** The principal is an AWS service
rather than a specific caller, so without that condition the statement allows *any*
account's budget or anomaly subscription to publish into this topic — the confused-deputy
shape. With it, a publish is accepted only when the service is acting for this account.

**The budget excludes credits and refunds.** Leaving `IncludeCredit` on lets a credit
mask real spend: the bill reads flat while usage climbs, and the alarm that should have
fired does not. For a guardrail you want to see usage, not the net.

**The anomaly threshold is absolute dollars, not a percentage.** On a small account a
percentage threshold fires on noise — $0.40 to $4 is a 900% jump and not worth an email.
On a large account 10% can be thousands of dollars and very much is. Dollars mean the
same thing at every account size.

**The monitor is DIMENSIONAL on SERVICE, not a single account-wide baseline.** It learns
a separate normal per service, so $40 of unexpected SageMaker reads as an anomaly even in
a month where the total happens to look ordinary. One whole-account baseline hides exactly
that case.

**Frequency is IMMEDIATE, which is also the only frequency that accepts SNS.** DAILY and
WEEKLY are email-only, so choosing SNS and choosing immediacy are one decision, not two.

**Budgets and Cost Explorer are pinned to us-east-1.** Both are global services with a
single endpoint; calling them anywhere else fails. The region is hard-coded rather than
read from the environment so that a developer with `AWS_REGION=eu-west-1` does not get a
confusing failure.

**`teardown` leaves the SNS topic in place.** The GuardDuty path may be publishing to it,
and deleting the topic would silently take that down too.

## Tests

```bash
python -m pytest tests/ -q     # 11 passed
python -m ruff check .         # All checks passed!
```

Both tools are version-pinned in `requirements.txt` - ruff exactly, pytest below the next
major. An unpinned linter fails code that has not changed on the day it adds a rule, which
is a red pipeline carrying no information. boto3 is deliberately left floating: the tests
validate request shapes against the service models boto3 ships, so a newer boto3 is a
stricter check rather than a flakier one.

Every call is served by botocore's `Stubber`, which validates each request against the
real service model — so a misspelled parameter or a wrong shape fails in CI rather than
at deploy time. That is why the request builders are pure functions returning dicts: the
interesting assertions are about the request, and they need no account to make.

The suite covers the topic policy's principals and account scoping, credits and refunds
being excluded, the actual/forecast threshold split, the absolute-dollar anomaly
expression, plan mode sending nothing at all, a full create path, the idempotent
re-run path, and an untaggable key being reported rather than swallowed.

**What the tests deliberately do not assert: that the alerts fire.** That needs real spend
in a real account over real time. Claiming it from a stubbed suite would be claiming
something these tests cannot see.

## IAM

`iam-policy.json` is the least-privilege policy for whoever runs the script. Replace
`ACCOUNT_ID` before use. Two notes on why it is not tighter: Budgets exposes only coarse
actions (`ViewBudget` covers describe, `ModifyBudget` covers create, update and delete),
and Cost Explorer actions do not support resource-level restriction at all, so those are
scoped by action. The SNS statement is scoped to the single topic.

## After deploying

**Confirm the subscription email AWS sends.** An unconfirmed SNS subscription silently
drops every message, which looks identical to having no alerts at all.

Cost Anomaly Detection needs roughly **10 days of spend history** before it has a baseline
to compare against, so expect silence from that control on a new account. Budgets works
from the first day.

Activating a cost allocation tag is retroactive in *reporting* but not in *tagging*: Cost
Explorer can group by that key only for usage recorded after the resources themselves were
tagged. Activating it late does not reconstruct attribution for spend already incurred
untagged — which is the argument for doing it on day one rather than when the bill first
surprises you.
